cidoc-crm-mcp

An introduction for people who model in CIDOC CRM and have never had to care what an MCP server is.

NO PRIOR SOFTWARE KNOWLEDGE ASSUMED  ·  COMPANION TO docs/how-it-works.html

1What it is, and how you use it

You do not use this software directly. Your AI assistant does, on your behalf, while you carry on asking questions in ordinary language.

If you have asked a chat assistant a CIDOC CRM question, you will know the failure. It answers immediately and fluently. It names a class. The class is plausible. Sometimes it is right; sometimes the property it suggests has a domain that forbids exactly the thing you asked about; sometimes it cites a class the standard retired years ago. Nothing in the answer tells you which of those you are looking at.

The problem is not that the assistant is careless. It is that nothing authorises its answer. It is recalling the CRM from memory, the way you might recall a scope note you last read in 2019.

This project gives the assistant somewhere to look instead. It is a small program that runs on a computer — yours, or your institution's — and offers twelve specific services to an assistant that asks. Look up a class. List every identifier in CRMsci. Find every property that can legally join an E21 Person to an E53 Place. Check whether this RDF file is legal CRM. Search twenty-six years of what the CRM Special Interest Group actually said.

Two things people use it for

One  ·  asking what the model says, and why

Which class is right for this, and what is the difference between it and the one next to it? Can this property legally join these two classes? Is what I have written legal CRM? And then the question the specification cannot answer at all — why is it like this? Why is production an event rather than a property of the object, what was proposed instead, who objected, and was it ever settled. That reasoning exists, in twenty-six years of committee argument, and this is the half that quotes it with names and dates.

Two  ·  turning what you already have into CIDOC CRM

A drawer of accession records, a collections database export, excavation reports, a pile of wiki articles — free text or somebody else's schema — that has to come out the other side as CRM. The assistant does the mapping; what this adds is that every link it writes can be checked before you believe it. Hand the validator the whole document, not a summary of it, and it answers for every triple: legal, illegal, or a name that is not a CRM property at all.

That check is what makes volume survivable. You can read ten converted records by eye; you cannot read ten thousand. And the commonest error is not an exotic one — it is a plausible-looking class name the standard renamed years ago, which reads perfectly well and is wrong in every record it touches.

The two uses run together more often than not: a conversion stalls on a question about the model, and the answer to that question is in the archive.

What an MCP server is

MCP stands for Model Context Protocol. It is an agreed way for an AI assistant to call out to a tool and get a real answer back, rather than recalling one. An MCP server is a program that offers such tools. The name is unhelpful in one specific way: it is not a website and there is nothing to log into. Think of it as a reference desk that only your assistant talks to.

You connect it once — one line of configuration in whatever assistant you use, shown in section 6 — and then you never think about it again. You ask your questions the way you always did. The difference is what happens in the seconds before you get an answer.

What a session actually looks like

You are cataloguing a photograph of a building. You ask your assistant how to model it. Before answering, it makes perhaps four calls you never see: it searches the specification for the relevant guidance, looks up the two classes it is choosing between, asks which properties can legally join them, and — once it has written some RDF — asks whether that RDF is legal. Then it answers you, and the answer says E36 Visual Item, and cites the section it came from, and you can go and read that section.

If your question is instead why the CRM is shaped this way — why production is an event rather than a property, what happened to E84 — the assistant reaches into the other half: the mailing list, where that was argued out, often at length, sometimes twice.

A conversion looks different only in scale. You hand over a batch of records, agree a mapping on the first few, and then the work becomes mechanical: for each record the assistant writes the RDF and submits the whole document to the validator, which answers for every triple rather than for the ones anybody thought to doubt. What comes back to you is the conversion plus a list of what did not pass — which is the part you actually have to read.

2The two halves, and why they are kept apart

One half computes what the standard permits. The other quotes what people said. Blending them would produce a more confident answer and a worse one.

The twelve tools are not one set. They divide down the middle, and the division is the single design decision everything else follows from.

The normative half — six tools

Answers computed from the CIDOC CRM's own machine-readable definition. When this half says P108 has produced runs from E12 Production to E24 Physical Human-Made Thing, that is not an opinion and not a recollection. It is read off the standard. When it says a link is illegal, the link is illegal.

The evidentiary half — six tools

Answers quoted from twenty-six years of CRM-SIG mailing list traffic, the issue register, and the meeting minutes. This half does not tell you what is correct. It tells you who said what, and when — including people who turned out to be wrong, which is exactly why the attribution matters.

A scope note tells you what a class is. It rarely tells you what it is for, which of two plausible classes the committee actually intends, or what was tried and rejected on the way to the current wording. That reasoning exists, but it exists in the archive rather than in the specification.

The temptation is to merge the two into a single confident answer. The tools refuse to. A claim from the normative half and a claim from the archive have different standing, and a reader who cannot tell them apart has lost the only thing that made the archive worth consulting.

The twelve

crm_concept
One identifier or label: definition, hierarchy, domain and range, its siblings, and how often the archive argued about it.
crm_list
Every identifier in one model, with the exact spelling to write in RDF.
crm_connect
Every property that can legally join two classes, both directions.
crm_validate_link
Is this one subject–property–object triple legal?
crm_validate_rdf
Check a whole model in Turtle, RDF/XML, N-Triples or JSON-LD.
crm_validate_xml
Check a whole document in the published CIDOC CRM example format.
crm_search
Search the mailing list.
crm_docs
Search the specification itself, the issue register, the minutes, or the Conceptual Modelling Principles.
crm_issue
One SIG issue by number: its status, its outcome, and every thread and meeting that discussed it.
crm_thread
Read a whole discussion in date order.
crm_show
Read one message, or one section of the specification, in full.
crm_quote
Verify that a quotation actually occurs in the source it is attributed to.

That last one deserves a sentence. An assistant that has read a long thread can reconstruct a quotation from memory and get it subtly wrong — and a human reviewer, reading the same thread, can be talked into confirming it. crm_quote decides the question mechanically instead: the phrase is in the message, or it is not.

Two things follow from these numbers that are easy to miss.

First, the specification is a small minority of the searchable text. The 244 declarations and 130 narrative sections sit in the same store as 6,646 sections of issue pages and minutes. Left to compete on size alone, the specification loses every time — so a search of the reference documents returns the specification by default, and the issue register and minutes only when asked for by name.

Second, the archive is not a neutral sample of opinion. It is the working correspondence of a standards committee. Some contributors post constantly; some questions were settled in one exchange and some were reopened for a decade. The volume of discussion about an identifier measures how contentious it was, not how important it is.

4Two kinds of search, and why one is not enough

Only two of the twelve tools search at all. Those two search everything twice, by methods that fail in opposite directions, and combine the results.

It is worth being exact about which half this concerns, because it is the sharpest difference between the two. The normative half does not search. When crm_connect tells you which properties join an E21 to an E53, it has not looked for likely-seeming ones: it has walked the class hierarchy and tested every property's declared domain and range. The answer is computed, and it is the same answer every time. There is no ranking, nothing was nearly included, and no passage had to be found.

Searching belongs to the other two tools — crm_search over the mailing list, and crm_docs over the reference documents. (The second of those searches the specification's own text as well as the issue register and the minutes; it is retrieval either way, which is what puts it on this side of the line.) What follows is about those two.

Suppose you want the discussion about controlled vocabularies. There are two ways a computer can find it, and each has a blind spot the other covers.

Keyword search, which is literal

The first method indexes the words as written and finds documents containing them. It is exact and fast, and it is the only thing on earth that can reliably find E55 — a short token, meaningless as English, that has to match precisely. Its blind spot is that it has no idea E55 and the phrase controlled vocabulary have anything to do with one another. Ask it for one and it will not show you the other.

Meaning-based search, which is associative

The second method converts each passage into a long list of numbers — an embedding — positioned so that passages about similar things land near one another, whatever words they used. It will find a message about controlled vocabularies that never once writes that phrase. Its blind spot is the mirror image: identifiers are gibberish to it. The model that produces these numbers does not know E55 as a word at all; it breaks it into a meaningless E and a 55, and cheerfully lands it next to E52 and E41, which are unrelated.

This is why, when you search, an identifier and a paraphrase both work, and why you do not have to know which kind of question you are asking. It is also why a search result and a validator's verdict should not be read the same way. One is the best of what was found; the other is what the standard says.

Where the material came from

The normative half is built from the CIDOC CRM's own published files — the v7.1.3 RDFS, the family-extension encodings, and the v7.3.2 text for the first-order logic and full-path expansions the older files do not carry. The evidentiary half is built from the public CRM-SIG list archive, the issue register pages, and the published meeting minutes.

Nothing was paraphrased on the way in. What the tools quote is what the sources say, and every quotation carries the identifier or thread it came from so you can go and check it. One step did use a language model: the 883 episode summaries, which condense a thread into what was asked, who argued what, and whether it was settled. Those are summaries and should be read as such — the underlying messages are always one call away, and the summaries exist to help you find them, not to replace them.

5What not to trust it for

A tool that tells you its limits is more useful than one that does not, and these limits are specific.

The archive records arguments, not conclusions

This is the big one. A search result is a thing somebody said on a mailing list. It may be a considered position from the CRM's principal author; it may be a first reaction that the next message demolished. The tools deliberately do not adjudicate. They give you the author and the date and the thread, and reading on is your job. Where a question was settled formally it was settled as a numbered issue — crm_issue is the tool that reaches the decision record rather than the debate.

The specification is domain-agnostic, and so are the answers

The CRM does not mention grave goods, ship burials or daguerreotypes, and it never will — enumerating concrete cases is precisely what its Minimality principle forbids. A subject-matter search of the specification therefore finds nothing, and that absence is itself the answer: model it from the generic classes. Mapping your actual object onto E36 or P62 is the modeller's job, and the assistant's. It is not something the specification will do for you.

"Not checked" is not the same as "fine"

When the validator reports a predicate as not CRM, or a subject as unchecked, it means exactly that: outside this validator's authority, or never examined, because the thing had no declared type to check against. Neither is an endorsement. This matters most for the commonest error an assistant makes, which is not an illegal link but a plausible-looking class name the standard renamed years ago.

The corpus has a date, and this document may not match it

Every answer is drawn from one build of the corpus, whose contents are fixed at the moment it was made. Discussion after that date is not in it. The counts in section 3 describe the build current when this was written; a running server reports its own provenance:

docker run --rm ghcr.io/stefdoerr/cidoc-crm-mcp:latest cat /app/corpus-provenance.json

There is no authentication

The server has no logins and no access control, by design — it is meant to run on your own machine and be reachable only from it. Anyone who can reach the port can search the whole archive. If you ever move it off loopback, put a proxy with a token in front of it first.

6Trying it

One command to run it, one block of configuration to connect it. Nothing to install, no corpus to download, no Python.

Everything — the code, the ontology and the whole corpus — ships in a single container image. Start it:

docker run -d -p 127.0.0.1:8000:8000 ghcr.io/stefdoerr/cidoc-crm-mcp:latest

Then tell your assistant it exists. Most tools take a block like this:

{
  "mcpServers": {
    "cidoc-crm": {
      "type": "http",
      "url": "http://127.0.0.1:8000/mcp"
    }
  }
}

That is the whole setup. The 127.0.0.1 is doing real work: it publishes the port to your machine only, which is the arrangement section 5 describes. In Claude Code the same thing is one line:

claude mcp add --transport http cidoc-crm http://127.0.0.1:8000/mcp

Ask your assistant a CRM question afterwards and you should see it consult the tools before it answers.

The advice it gives is a file you can argue with

The server ships a modelling brief — the instructions an assistant reads before working through a model with you. It is advice, it was wrong in ways only real modelling runs revealed, and it will be wrong again. So it is a file rather than something buried in the program. Mount your own directory over it and your version wins, re-read on every request, with no rebuild and no restart:

docker run -d -p 127.0.0.1:8000:8000 \
  -v "$PWD/prompts:/prompts:ro" ghcr.io/stefdoerr/cidoc-crm-mcp:latest

If you disagree with how it tells an assistant to approach a model — and if you model in CRM seriously, you will — that is the file to change.
