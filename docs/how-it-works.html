What this is, for people who model in CIDOC CRM

A modelling assistant is only as good as what authorises its answers. This repository gives an assistant twelve tools and wires every one of them to a source you can go and read: the normative RDFS on one side, twenty-six years of what the SIG actually said on the other.

The picture

The twelve tools

Click any tool in the diagram — or any entry below — for what it does, a real call, and the output that call returns. Every output quoted here came out of mcp_server.py on this build; nothing is illustrative.

What is it? — the normative layer

crm_conceptone identifier, in full

Everything the specification says about one class or property, assembled from the normative RDFS and the presentation XML: scope note, place in the hierarchy, domain and range, the CRM’s own examples, siblings, and every applicable property with the necessary ones marked. Then, from the archive, where the SIG argued about it — which is the one place the two halves of the system meet in a single answer.

How it works

A dictionary lookup in data/ontology.json — the file xml.etree.ElementTree produced from the specification XML, with CIDOC’s RDFS folded in — then three structural walks over it: siblings from the parent’s subclass list, applicable properties from the domain and range closure, and the archive count by counting the messages tagged with that identifier. Nothing is embedded, scored or ranked. The episode list at the end is the one model-written thing on this page; see figure 3.

crm_listevery identifier in one model, spelled as RDF

The answer to “what exactly do I type”. One call spells every identifier in a model as it must be written in RDF — local name, inverse name, namespace at the top — so a modeller never has to guess whether it is E22_Man-Made_Object or E22_Human-Made_Object. Identifiers the archive attests but no current declaration defines are marked as such rather than quietly dropped.

How it works

One pass over the merged model view — CRMbase and the eleven family models in a single dict — sorted and formatted. The local name is composed from the identifier and its label (E22 + “Human-Made Object” → E22_Human-Made_Object), which is also the key the URI index is built on, so the name this prints is exactly the name every other tool will accept.

May I write it? — the normative layer

crm_connectevery property that can join two classes

Two classes in, every property that can legally join them out — in both directions, and with the CRM’s own declared full path printed underneath any shortcut. That last part is the point: a modeller can see that P52 has current owner is the Acquisition path collapsed into one link, and choose the shortcut or the path deliberately instead of discovering the difference later.

How it works

Two ancestor sets, computed by walking sub_class_of with an explicit visited set — the CRM hierarchy is a DAG rather than a tree, since E22 is both an E19 and an E24, and a naive walk revisits shared ancestors — then every property whose declared domain lands in one set and range in the other, in both directions. The full paths are not inferred: they are read out of the declaration’s own text in the published specification.

crm_validate_linkone triple, checked

One subject–property–object triple, checked against domain and range. It reports every reading of an ambiguous property label rather than picking one, says whether the CRM quantifies the property as necessary on its domain, and when no reading is legal it says the thing a CRM modeller actually needs to hear.

How it works

The name is resolved to every reading it could have — an identifier, an inverse identifier, an RDF local name through the URI index, the identifier beside its own name, or a bare label — and then each reading’s declared domain and range is tested for membership in the subject’s and object’s ancestor sets. Set membership, not inference. Fourteen labels are shared between properties (“consists of” is P5, P9 and P45), so an ambiguous name is reported with every reading rather than resolved by guess.

Input

{"subject": "E79", "crm_property": "added", "object_class": "E52"}

Output

E79 --added--> E52
  no     P111     added                               E79 -> E18
         E52 is not a E18
         (the CRM quantifies this as necessary on its domain)

No reading of this link is legal. In the CRM that usually means
the relationship runs through an event -- try `connect` on the two
classes to see what does join them.

And the legal case

{"subject": "E79", "crm_property": "P111", "object_class": "E22"}

E79 --P111--> E22
  LEGAL  P111     added                               E79 -> E18
         domain and range both admit these classes
         (the CRM quantifies this as necessary on its domain)

The property can be named any way the other tools print it — an identifier (P111), its RDF local name (P111_added, as crm_list spells it), a full URI, a crm: name, a bare label (added, was added by), or the identifier beside its own name (P111 added, as the columns above print it). A pair that disagrees is refused rather than resolved: P111 augmented answers no property matches — P111 is ‘added’, because taking the id and discarding the name would report LEGAL about a property the caller never asked about. From a terminal: uv run python search.py validate E79 added E52

crm_validate_rdfa whole RDF model

A whole model in Turtle, RDF/XML, N-Triples or JSON-LD, checked link by link: every domain, every range, every rdf:type, and every owl:inverseOf claim the file makes. It reports the offending subject URI, not just a count, and it fails loudly enough to gate a pipeline.

How it works

rdflib parses the document, every triple becomes a link in the same shape the example-format reader produces, and each one goes through the single-triple check above — one checker, two formats. rdf:type assertions are checked as class names and owl:inverseOf claims against what the CRM actually declares: the two kinds of assertion a link check on its own would walk straight past.

crm_validate_xmla whole document in the CRM’s own example format

The same check for the format the specification’s own published examples are written in, where property labels are the element names. It checks the labels exactly as written, not a normalisation of them, so a stale label like E22: Man-Made Object is caught. It also separates a real error from a limitation of the format — which matters, because one of them is the modeller’s fault and the other is not.

How it works

xml.etree.ElementTree walks the published example format — element names are property labels, in_class text names the class — and converts it into the same link shape the RDF reader produces, so the checker underneath is the same one. The labels are compared as written rather than as normalised, which is the only way a stale E22: Man-Made Object can be caught at all.

What is it for? — the evidentiary layer

crm_searchtwenty-six years of SIG discussion

Where the ontology tools say what a class is, this says what it is for: which of two plausible classes the SIG actually intends, why a property exists, what was tried and abandoned. Each hit carries its date, its author, its thread, and the CRM identifiers it mentions, so a modeller can judge the weight of an opinion before adopting it — a 2002 message and a 2022 one are not equal evidence.

How it works

The retrieval stack in figure 3, over 2,000-character chunks with 200 of overlap: SQLite FTS5 for BM25 beside a Chroma index of gte-modernbert-base embeddings, the two rankings fused by reciprocal rank fusion. Nothing summarises the hits — each one is the archive’s own text with the id that fetches the rest of it — and no more than two hits come from any one thread, because the third is one crm_thread call away and the slot is better spent on a different voice.

crm_docsthe specification, the register, the minutes, the principles

The same retrieval over the written record rather than the correspondence: the v7.3.2 specification text, both its declarations and its narrative guidance, and — selected by kind — the issue register, the SIG meeting minutes, or the Conceptual Modelling Principles. Ask it the modelling question in your own words and it returns the paragraph of the specification that governs it.

How it works

The same stack over a different store, plus one default that exists because volume would otherwise decide the ranking: the specification is 374 chunks in a store of about 7,000, so docs searches declarations and narrative unless a kind says otherwise. Bibliography-shaped chunks are excluded by default as well — 43 of them, 0.6% of the corpus, which took two of the top five slots on an archaeology query, which is how they came to be excluded.

Was it settled? — the evidentiary layer

crm_issuethe decision record

If a modelling question was ever settled formally, it was settled as an issue. This returns one issue by number: its status in the register, the SIG’s own words for the outcome, every thread that discussed it, every meeting that took it up, and the issue’s own cross-references. It is the difference between “someone on the list once said” and “the SIG decided”.

How it works

Not retrieval at all — an index built at build time. A regex requires the word “issue” immediately adjacent to the number, and the number is then validated against the register scraped from cidoc-crm.org. Both guards are needed: issue numbers run 1 to 722, so almost any small integer near the word is coincidentally a real id (“issue 43, 3rd draft” is an ordinal, not a second issue). What it reports as status is the register’s own field, never a reading of the debate.

crm_threada whole exchange in date order

A search hit is one message out of an argument. This returns the whole thread in date order, numbered, so the reasoning can be read as it happened — including the messages that walk back the first proposal. Worth the call whenever a hit looks like it settles the question you are stuck on.

How it works

Threads are reconstructed at build time from three signals: reply-chain headers, quote overlap, and subject match — the last two under a time guard, because subject-only matching glued several unrelated debates into one bogus 33-message “issue” thread. Messages then print in date order from the cleaned records, de-quoted by rules keyed on how many quote blocks a message has, so each reply shows what its author wrote rather than the thread re-quoted beneath it.

crm_showone message or chunk, in full

A search result is a fragment. This returns the whole of one message, or one document chunk, by id — with its date, author, subject and the CRM identifiers it mentions. It is how you check that a snippet means what it appeared to mean in a list of results.

crm_quotedoes this phrase actually occur?

The tool that exists because a plausible quotation and a real one look identical. Give it a phrase and a source — thread, message, episode or document chunk — and it answers whether the phrase is genuinely there, showing it in context with the match marked. When it is not there, it says how close the nearest passage got, which is usually enough to see where the paraphrase drifted.

How it works

A substring match after whitespace and quote characters are normalised, with elided quotations supported: fragments separated by … or […] must occur in order, and each must carry at least four words or it is not treated as an elision at all. When that fails, difflib.SequenceMatcher(autojunk=False) reports the longest contiguous run of the phrase the source does contain, as a fraction of the whole. That number is diagnostic only — it is never promoted into a FOUND, which is the entire discipline of this tool.

The same question, actually asked

Figure 1 is not an illustration of an intention. Every step below is real output from this repository, in the order a modeller would reach for it. The decision it records is in models/crm_bayeux_notes.md.

1. What is it? crm_concept E79 returns the scope note, and the scope note settles it:

Both the E18 Physical Thing being augmented and the E18 Physical Thing that is being added are treated as separate identifiable wholes prior to the instance of E79 Part Addition.

with E12 Production and E80 Part Removal named as siblings under E11, 57 outgoing and 52 incoming properties, and P110 augmented and P111 added flagged as necessary. The 1724 backing cloth was such a separate whole, so it is an E79. The spurious final titulus, embroidered straight into the cloth and never a whole of its own, is an E11 Modification. Same object, two events, two classes — and the scope note, not taste, is what divides them.

    P16   used specific object                E7  -> E70
    P8    took place on or within             E4  -> E18
      Full path: E4 Period. P7 took place at (witnessed): E53 Place.
                 P156i is occupied by (occupies): E18 Physical Thing
    …five more, and three in the E22 -> E79 direction

3. What is it for? crm_search over the list. The fourth hit is from January 2002:

That is the class being created, in the words of the meeting that created it — including the range it originally had, which is not the range it has now.

4. Was it settled? Another hit points at ISSUE 191. crm_issue 191 returns the decision record: Range of P31, status Done, closed 2018-05-25, with the SIG’s own statement of the outcome —

— plus the three threads that discussed it, between 2010 and 2021, and the five SIG meetings that took it up. This is why the 2002 quotation says E24 and the current specification says E18: the range was formally changed, in Lyon, in May 2018. A modeller reading the 2002 message alone would have got it wrong; the issue register is what tells them the discussion moved.

5. Before citing any of it. Each of those results prints the command that verifies it, down to the anchor in the minutes:

crm_quote answers only whether the phrase is genuinely there, in context. It exists because a plausible quotation and a real one are indistinguishable until something checks, and an assistant that paraphrases the SIG into something it never said is worse than no assistant.

How an answer is made

The twelve tools run on two engines, and which one answered you decides how much weight the answer can bear. Half the tools compute from the normative RDFS: the same question returns the same answer on every machine, and it is wrong only where CIDOC's own RDFS is. The other half retrieve: they rank passages by statistical similarity, which can put the wrong passage first — but the passage itself is the archive's own text, printed with the identifier that fetches the rest of it.

The bottom panel is the claim worth checking hardest, because it is the one that would matter most if it were false. No tool sends the corpus to a model and prints what comes back: an answer about legality is computed from the RDFS, and an answer about intent is a passage lifted whole, with the id that lets you fetch it and the crm_quote call that proves the phrase is really in it. The episode summaries are the exception, and they are labelled as one wherever they appear.

BM25 and Chroma, if you have not met them

Neither is CRM-specific, and both are doing something narrow enough to state exactly.

BM25 is a scoring formula for literal word matching — “Best Match 25”, the twenty-fifth formula in a series from the Okapi project in the 1990s, and still the default ranking in most library catalogues. It answers one question: given these query words, which passages look most about them, judged on the words alone? Three behaviours do the work. A rare word counts for more than a common one, so “posthole” carries a query and “the” carries nothing. Repetition saturates, so a tenth occurrence adds almost nothing over the third. And length is normalised, so a long passage cannot win merely by containing more words. (The last two are BM25's only tuning constants; SQLite fixes them at the standard values, and nothing here changes them.) What it cannot do is know what a word means: to BM25, “controlled vocabulary” and “E55 Type” have nothing whatever in common.

Here it is SQLite's FTS5, which ships inside Python's own sqlite3 and so costs no dependency. Two things about it are our choices rather than the formula's. The tokenizer is unicode61 with diacritics folded, which keeps E55 and P140 as single tokens. And the fields are weighted: each chunk's list of CRM identifiers counts four times, the subject line twice, the body once, and the sender's name zero — because a query mentioning “Martin” should not drag in every message Martin ever sent.

Chroma is a vector database — the store for the other half. The embedding model turns each passage into 768 numbers: a point in a 768-dimensional space, positioned so that passages about the same thing land near one another whether or not they share any words. Chroma holds those points and, given the query's point, returns the nearest, measuring distance as the cosine of the angle between them and using an approximate-nearest-neighbour index (HNSW) so a lookup need not compare against every chunk. The model is gte-modernbert-base, whose 8,192-token window comfortably holds a 2,000-character chunk, and each store records which model built it so the query side cannot silently use a different one.

What each is blind to is easier to show than to describe:

what you type BM25 on its own the vectors on their own
P31 P31's own declaration and every passage that cites it — exact and complete, because P31 is one token and either a passage contains it or it does not. Very little. P31 is not a word: the model splits it into P and 31, which mean nothing, and the nearest points are other identifiers — which is how a query for one identifier lands on its neighbours instead.
“how do I model a photograph of a building” Passages that happen to contain photograph and building, many of them incidentally, and nothing at all from the passages that answer the question in other words. The E36 Visual Item / P62 depicts / P138 represents guidance, which contains none of the words you typed.

Hence the weighting that shifts with the question: name an identifier and the exact match is the strongest signal available, so the two fuse evenly; name none and BM25 has nothing to bite on, so the vectors carry twice the weight. Both indexes hold exactly the same rows — 8,855 message chunks, 7,086 document chunks, 883 episode summaries — so when they disagree it is always about scoring, never about one of them not having seen the text.

And why the two are fused by position rather than by score. The numbers are not comparable: FTS5's BM25 score is negative, and more negative is better; cosine similarity runs from −1 to 1. Adding them would be meaningless, and rescaling them into a common range would invent a precision neither has. Reciprocal rank fusion throws the scores away and keeps only the positions — each ranking contributes 1/(60 + rank), and the sums decide. The practical effect is that agreement outranks enthusiasm: a chunk both engines place third (1/63 + 1/63) finishes above one that is first in a single list and absent from the other (1/61).

Where the material comes from

Two things worth knowing before you trust it

  • The two halves are not interchangeable. The ontology half computes from the normative RDFS, so its answers about legality are as good as v7.1.3 itself. The archive half quotes people arguing, including people who turned out to be wrong, and its value is that it says who and when. A scope note and a 2003 mailing-list opinion are not the same kind of authority, and the tools keep them apart rather than blending them into one confident answer.
  • A draft is marked as a draft. The Conceptual Modelling Principles are a working document at v0.1.2. Their 66 chunks are held under their own kind, so they never compete with the published specification in a default search — because a reader who cannot tell a draft principle from a normative one will weight them alike.

How it is reached

The same twelve tools, two ways. mcp_server.py speaks MCP over stdio, so an assistant holds the ontology and the embedding model in memory once per session instead of reloading them on every question. search.py is the same functionality as a command line, which is how every output quoted above was produced — and how anyone can check it.
